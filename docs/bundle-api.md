# Velmora bundle contract, version 1

`catalogue.py` is authoritative for product identity, declared colours, photography, sizes, price and availability. `bundles.py` stores references to that catalogue and resolves them for every UI and API. `Bundle`, `BundleItem` and their validation functions are shared by curated sets, customer drafts, future AI proposals, previews, the product switcher and the bag. The JSON input contract is in `schemas/bundle.schema.json`; runtime validation also enforces catalogue relationships, size membership, availability, contiguous unique positions and the budget. Prices are GBP. `pricing.py` is the shared authority for active preview campaign prices; original prices come from the catalogue.

A local `variant_id` identifies a declared colourway, for example `VLM-048--emerald`, with `colour_id: "emerald"`. Size is a separate selection; it may be null while browsing a dress and is required before adding that dress to the bag. One-size accessories resolve to `"one size"` automatically. IDs are derived from existing declared colours, including single-colour products. They are not stock quantities or third-party commerce SKUs. A future commerce adapter must map these colourway and size pairs to verified external variant IDs before any real checkout is enabled.

A stored bundle has an ID, name, optional description and occasion, origin (`curated`, `customer-created`, `AI-generated`), optional colour palette and budget, timezone-aware creation/modification timestamps, draft/publication status and schema version. Every item must supply `product_id`, `variant_id`, `colour_id`, quantity and zero-based position, with optional size and styling explanation. Read responses resolve the colour label, product name, category, current unit and line prices, selected-colour image paths, availability and size requirements. `purchasable` requires all items to be available and all clothing sizes chosen. It describes selection readiness, not an operational checkout.

`tests/fixtures/bundle-proposal.json` is a reference-only, catalogue-valid example. `tests/fixtures/styling-request.json` is a structured customer request. Test providers exist only in tests and are never used as a fake live model.

## Browser and session contract

`GET /api/session` returns a CSRF token and `styling_enabled`. POST requests require that session cookie and `X-CSRF-Token` for JSON, or the `csrf_token` form field. Supply `Content-Type: application/json` for API mutations. Body size is limited to 32 KiB. Prompts are limited to 2,000 characters and have structured field/type limits. Cross-origin mutations are rejected. Responses containing shopping state are not publicly cached.

The bag is stored as signed cookie references, re-resolved against the current catalogue on every read. It holds at most 15 distinct colour/size selections and at most 20 of each selection, with exact duplicates merged. `POST /bag/items` accepts the actual product ID, matching colourway ID, colour ID and chosen size; client prices and stock are never used. Missing sizes and unavailable colourways return 422. Native forms redirect to `/bag`; JavaScript receives JSON and updates the visible bag count. `POST /bag/remove` removes the selected line. `GET /api/bag` exposes the visitor's resolved bag.

Selections in `/bundles/<slug>?item=2&colours=champagne/pewter/emerald&sizes=UK+10/one+size/one+size` are visitor customisations. They never modify the curated definition. Colour changes push browser history; size changes replace the current selection state. Every wardrobe/swatch link carries current selections. Back/forward fetches the complete corresponding product view. Requests are aborted and sequence-checked so a slow previous request cannot overwrite a newer product. A failed history request hides a view that no longer matches the address and provides a direct reload link. Regular links and purchase forms remain functional without JavaScript.

`/bundle?items=VLM-003/VLM-047/VLM-048` and its ordered, repeated product IDs remain supported. This legacy adapter explicitly resolves the catalogue's photographed default colourway into the shared model. New creators must submit explicit colourway references; product-ID-only input is rejected by the saving and generation validation paths. Do not use the legacy adapter to accept new model output.

## Generate a proposal

`POST /api/bundles/generate` accepts the styling request fixture's shape. Only `prompt` is mandatory. Optional fields are `occasion`, `preferred_colours`, `budget_gbp`, `size`, `categories`, `materials`, `season`, `aesthetic`, `starting_item`, `current_items` and `promotion_preference` (`any`, `prefer`, `only`, `exclude`, `ignore`). `starting_item` contains a required `product_id`, `variant_id` and `colour_id`, with optional `selected_size` and `quantity`; the model must preserve this real available piece and its colour, quantity and selected size. `current_items` carries the same reference shape for refinement; the new `prompt` supplies the requested change. Unknown fields, invalid types and non-finite budgets are rejected. The response is `{ "proposal": <resolved bundle or null>, "constraints": [], "alternatives": [] }`. No catalogue records, bags, orders or stored bundles are modified by generation.

`BundleGenerationService` separates request validation, interpretation, eligible catalogue retrieval, suggestion, catalogue validation, total calculation and response construction. A `StylingProvider` adapter supplies `interpret(request, timeout_seconds=...)` and `suggest(brief, catalogue, timeout_seconds=...)`. The provider receives genuine available colourways, sizes, fabric, fit, occasions, making time and current price. The backend enforces structured category, size and budget constraints and every returned reference, even if a model disregards its instructions. Requested colour families constrain eligible variants; an untrusted provider cannot replace a requested colour with an unrelated one. The service never relabels a real colour with a requested name. With no eligible candidates, the proposal is null and the constraint is explicit. Alternatives are reserved for validated future recommendations.

When the provider is not enabled and fully configured, the route returns HTTP 503 with `code: "provider_not_configured"`. Provider failures, invalid interpretation, invented products/colours, unavailable variants, wrong sizes and over-budget proposals produce controlled HTTP 502 errors with no shoppable proposal. Adapter timeouts return a safe timeout message. Customer prompts, raw provider output and credentials are not included in application logs or storage; only the failure class is logged. A configured model will necessarily receive the customer's prompt, so the future input interface must explain that processing and its retention policy before use.

The concrete `OpenAIStylingProvider` uses the Responses API with [strict structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), a fixed HTTPS origin, `store: false`, a request timeout, bounded responses and safe handling of refusals and invalid output. Its schema contains only product/variant references and styling copy. The model may extract an explicit GBP budget from the prompt, which the backend validates against real totals. Customer-supplied structured budget and size constraints always take precedence. Every returned reference is independently validated, the required starting piece is checked again and duplicate products are rejected. No SDK is required. The adapter is currently disabled and has only been tested with a mocked HTTP transport; a real account, supported model and live integration test are still needed.

To activate after provisioning credentials, set `OPENAI_API_KEY` in the server environment or secret manager, set `VELMORA_AI_PROVIDER=openai` and `VELMORA_AI_MODEL` to an available model that supports Responses structured outputs, and set `VELMORA_AI_ENABLED=1`. Optional `VELMORA_AI_MAX_OUTPUT_TOKENS` is 256–4096 (default 1600); `VELMORA_AI_TIMEOUT` sets the total provider deadline in seconds (1–120, default 20); `BUNDLE_PROVIDER_TIMEOUT` can alternatively be supplied in app configuration. Restart the server and test a genuine request against the live catalogue before exposing the feature. Missing or invalid configuration fails closed. Keep keys out of source files and browser code. Other vendors can implement `StylingProvider` without changes to the bundle model. The existing test-only `BUNDLE_PROVIDER`/`BUNDLE_PROVIDER_TESTED` injection remains supported.

`static/bundle-service.js` is the future frontend service boundary. It exports cancellable `generate`/`save` methods, typed service errors and `bundleReferences(proposal)` to strip derived catalogue fields before saving. The styling interface obtains a CSRF token and submits requests through the same provider-independent endpoint. Generated results must remain customer-editable and can be confirmed as a reference-only draft. Saved or published generated bundles use the same product view, swatches, gallery, compact navigator and bag controls. The interface clearly marks AI styling as coming soon while the provider is disabled.

## Confirm, save and publish

`POST /api/bundles` accepts reference-only data under schema version 1 and validates it against the current catalogue again. Generated read payloads include derived fields; use `bundleReferences` before saving them. The server assigns a fresh ID and authoritative timestamps. Saving returns HTTP 201 with `{ "bundle": <resolved bundle>, "url": "/bundles/saved/<id>" }`. This does not initiate a purchase.

Drafts are durably stored in SQLite at `BUNDLE_DATABASE` (default `instance/bundles.sqlite3`) and bound to the visitor's signed session identity. Another visitor receives 404 for a private draft, including via `GET /api/bundles/<id>`. Draft links work for their owning session; they are not public shared links. Named curated sets are available via `GET /api/bundles/winter-soiree`. To publish, configure `BUNDLE_PUBLISH_AUTHORIZER` to enforce the real authenticated editor role. Publishing is denied by default. Published records can then be opened using the returned link by another visitor. No editor authentication system is invented by this implementation.

A saved colourway that is later retired remains displayed with its original colour label and an unavailable state; another colour is never substituted. Current stock changes also make the relevant selection unavailable. New invalid or unavailable combinations cannot be saved or added to the bag. Product removal produces an unavailable bag entry rather than silently dropping a purchase selection. The catalogue itself rejects missing colour data at startup so it must be corrected in source data, not guessed in the UI.

## Deployment and commerce boundary

Set a persistent, high-entropy `VELMORA_SECRET_KEY` before deployment. Without it the development app creates a new key at process startup, invalidating previous session ownership/bags after a restart and preventing multi-worker session consistency. Enable `VELMORA_COOKIE_SECURE=1` with HTTPS. Retain the SQLite database on durable storage and back it up; account-based draft recovery and migrations can replace the session ownership adapter later.

The default bounded limiter limits generation to 10 requests per IP per minute and other mutations to 60 per IP per minute, independently by endpoint. It cleans idle keys, is thread-safe and is suitable for the local single-process app. Before a public multi-worker launch, inject a shared `BUNDLE_RATE_LIMITER(key, limit)` with deployment-wide storage and configure trusted proxy handling. `BUNDLE_GENERATION_AUTHORIZER(request)` can enforce customer authentication, membership or a spend policy before invoking a provider. The publication authorizer must use actual application identity, not customer-supplied role fields.

The original app had no checkout, orders or external commerce integration. The studio can add an entire validated set atomically to the working bag, preserving colourway, size and quantity; payment and checkout are not connected. Future checkout must revalidate all items, require remaining sizes, map real external variants and respect genuine pricing rules atomically. Demo preview discounts are explicitly labelled and never used as payable bag/checkout prices. Inventory quantities, shipping charges and order confirmations are not fabricated.

Availability currently inherits product-level catalogue data unless an explicit `variant_availability` mapping is supplied by canonical colour ID with values `in_stock`, `made_to_order` or `unavailable`. This allows a single colourway to become unavailable without affecting others. Size-specific inventory and commerce SKUs need additional authoritative data. Multiple genuine photographs of the same colour are supported; duplicate photograph paths, unknown colours and missing files are rejected. A preview without a selected-colour photograph uses a placeholder, while the main gallery labels any fallback photograph's actual colour. No image is recoloured or fabricated.


## Current promotion prices

`BLACK_FRIDAY_ENABLED` is read from current server configuration on every pricing/ranking operation, including after provider latency. `PROMOTION_RANKING_WEIGHT` becomes the provider's `promotionRankingWeight`, bounded to 0–0.5. The bonus cannot bridge a whole catalogue relevance step. Studio retrieval retains category diversity with at most four products per category and 48 variants; semantic search sends at most 24 products. The same campaign service supplies both flows and the shared bundle resolver. Provider output cannot supply trusted prices or discount percentages.

Resolved item payloads add `original_price_gbp`, `promotional_price_gbp`, `discount_percentage`, `promotion_active`, `campaign_id`, `promotion_label`, `preview_only`, `original_line_price_gbp`, `checkout_unit_price_gbp` and `checkout_eligible`. `unit_price_gbp` is the current preview unit price and `price_gbp` remains the quantity-aware line price. Bundle payloads add `original_total_price_gbp`, `total_savings_gbp`, `checkout_total_price_gbp`, `preview_only`, `pricing_notice`, `previous_total_price_gbp`, `price_changed` and `price_change_notice`. These derived fields must be stripped before saving using the existing reference helpers. `purchasable` continues to describe selection readiness for the bag; `checkout_eligible` is false for demo-discounted selections.

`POST /api/bundles/resolve` accepts the same reference-only model and returns current resolved prices without saving. It permits an over-budget or unavailable preview and reports `within_budget`/availability; saving and bag operations still enforce their normal constraints. It uses the existing CSRF and mutation limits. The studio refreshes visible prices every 30 seconds and on focus. Search results are not cached in the browser. Saved bundle reads do not reject an old budget when the campaign ends; they preserve selections, show the new total and mark `within_budget: false` where appropriate. A separate SQLite historical-total table supports change notices without storing copied product or discount data in bundle references.

`data/black-friday-demo.json` is the sole shared demo campaign. Every discounted price carries preview metadata. The bag always resolves ordinary prices and explains that the preview discount is excluded; online checkout is not connected. `purpose="checkout"` quotes ignore demo campaign rules unconditionally. A real checkout adapter must provide authoritative genuine promotion eligibility and prices before any live offer can be accepted.


The on-site **Black Friday demo** switch submits `POST /demo/black-friday` with a boolean `enabled` in JSON (or `"true"`/`"false"` in its native form), protected by the same CSRF/origin checks as other mutations. It stores a signed visitor-session override, leaving the server default and other visitors unchanged. The shared pricing service reads this override for every request; no client prices are accepted. Native forms redirect to a local return path. Enhanced Studio and catalogue pages refresh prices/results in place; the Studio ignores generation responses from a previous demo mode. The switch is visible below the navigation on desktop and mobile.
